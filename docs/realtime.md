# WebSocket (real-time)

- **Endpoint.** API Gateway WebSocket API on its own subdomain. Not proxied through CloudFront (WS bypass) — clients connect directly to `wss://<ws-api-id>.execute-api.us-east-1.amazonaws.com/prod`. Exposed as `WebSocketEndpoint` CfnOutput from `WebSocketStack`.
- **Auth.** JWT passed as `?token=<access_token>` query param on the `$connect` handshake; verified by `src/lib/ws-auth.ts`. WS does **not** enforce the `x-origin-verify` shared secret that the HTTP API uses: the WSS endpoint bypasses CloudFront (direct client → API Gateway) and browsers cannot set custom headers on WebSocket handshakes, so there is no delivery path for the header. Handshake security relies on the signed JWT + mandatory TLS. Unauthenticated connects are rejected at handshake — no DDB row is written.
- **Channels.** `user:<userId>` is always attached at connect; regular users also get `business:<businessId>` and one `branch:<id>` per `branchIds` on the token. Super_admin gets only `user:<userId>` and must opt in to `business:<id>` via `subscribe`. Dynamic `subscribe`/`unsubscribe` go through `$default` and are validated with `canSubscribeTo` from `@kaipos/shared`.
- **Connection store.** DynamoDB table `ws-connections` (PK `connectionId`, SK `channel`, GSI1 `channel-index`, TTL 2h). Populated by `$connect`, mutated by `$default`, cleaned up by `$disconnect` and inline by `publishToChannel` on `GoneException` (410).
- **Publish helper.** `apps/backend/src/lib/ws-publish.ts` exposes `publishToChannel(channel, message)` and `publishToUser(userId, message)`. The `api` Lambda is granted `execute-api:ManageConnections` on the WS API and read/delete on the connections table; use these helpers from services (e.g. `orders.updateOrderStatus` fans out `order.status-changed` to `channelFor.branch(branchId)`).
- **Frontend.** Shared by admin + POS via `packages/app-runtime`: `src/lib/ws-client.ts` (`WSClient`) handles connect, exponential backoff reconnect (1s→30s cap, ±20% jitter, max 10 attempts then terminal `'failed'`), and re-subscribes tracked channels on reconnect. Every *re*connect obtains a fresh token via `getFreshAccessToken` (refreshes when near expiry; no session → `'failed'` instead of dialing with a dead JWT). `src/hooks/useWebSocket.ts` wraps it for React; each app shell owns a single `WebSocketProvider` (`src/context/WebSocketContext.tsx`) so all consumers share one socket. Debug page at `/debug/ws` (admin, `platform:manage` only).
- **Consuming the context (incident 2026-05-06).** The context is split: `useWebSocketActions()` returns an **identity-stable** object (`connect`/`disconnect`/`subscribe`/`unsubscribe`/`ping`/`onMessage`/`setEndpoint`) that is safe in `useEffect` dependency arrays; `useWebSocketState()` returns the reactive `{ status, subscribedChannels, endpoint, hasEndpoint }`. **Never** put a merged ws object in an effect's deps: the old merged context changed identity on every subscribe, and a `useEffect(..., [ws])` around subscribe/unsubscribe looped at render speed — one tab drove ~6,000 `ws-default` invocations/min, saturated Lambda concurrency and 503'd the HTTP API. Depend on the primitive you read (`state.status`) plus the actions object, nothing more. `useWebSocketContext()` (merged) is deprecated.
- **Cost guardrails.** Client: jitter + retry ceiling + token refresh (above). Server: `$default` enforces a per-connection limit of 60 msgs/min per warm container — on breach it logs, force-closes the connection (`DeleteConnection`, which triggers `$disconnect` cleanup) and returns 429. Infra: the WS stage is throttled to 20 rps / burst 50 across all routes, the WS Lambdas run with reserved concurrency (5/2/5), and a `ws-fn-invocations` alarm plus a $5/mes AWS Budget catch anything that slips through (see `docs/observability.md`).
